# 4.5 — Prompt Kind Evidence: Dynamic Classification with Append-Only Evidence

**State:** in progress — R1-R4 prerequisites landed; evidence table not yet implemented
**Layer:** 4 (night-shift pipeline queue)
**Dependencies:** Route B (heuristic classification, merged). Spec 00 (consolidation).
**Parent analysis:** `problems/2026-08-08-session-prompt-classification-gap.md`
**Understanding doc:** `docs/session-prompts-schema-and-linking.md`

## Problem

Route B added heuristic prompt classification — `classifyPromptKind()` maps prompt text to
semantic kinds (debugging_request, question, correction, refactoring_request, follow_up),
and the reducer overrides the first user prompt to direction_setting. This is a one-shot
classification: the kind is baked in at insert time and never changes.

But classification is a belief, not a fact. A prompt that looks like a `question` at insert
time might turn out to be a `debugging_request` when the assistant's response reveals the
user was reporting a bug. A `follow_up` might turn out to be a `correction` when the next
user message says "no, I meant...". The classification should update as evidence arrives.

The system already has this pattern: lesson-delta uses append-only evidence with derived
beliefs (Specs/3). Zone associations use upsert with delta computation. The prompt
classification system should follow the same discipline.

## Unclosed Loops

Four loops must be closed for dynamic classification to work end-to-end. A loop is
"unclosed" when data flows in one direction but nothing completes the circuit.

### Loop A: Frozen classification

**What happens:** `classifyPromptKind()` runs at insert time. The kind is written to
`session_prompts.prompt_kind`. Nothing ever updates it.

**Why it's a problem:** The initial classification is the weakest evidence — it's based
on the prompt text alone, without context. Later evidence (assistant response, tool calls,
user corrections, outcomes) is stronger but has no way to influence the stored kind.

**How Route C closes it:** Evidence rows accumulate in `prompt_kind_evidence`. A
recompute step derives the current argmax and updates `session_prompts.prompt_kind` when
it changes.

### Loop B: No analysis consumer

**What happens:** `prompt_kind` is written but the only consumer is
`final-claim.ts:28`, which uses it as a structural filter (`WHERE prompt_kind =
'assistant_response'`). Nothing reads the semantic kinds for pattern analysis.

**Why it's a problem:** Without a consumer, classification is write-only — effort spent
classifying produces no value. This is the same loop documented in the gap analysis.

**How Route C closes it:** Route C does not itself add an analysis consumer. It ensures
the classification is trustworthy enough (via evidence accumulation) that a future
consumer can rely on it. The consumer is a separate work item.

### Loop C: No re-classification trigger

**What happens:** The hook pipeline fires `UserPromptSubmit` → adapter → reducer →
insert. Later, `Stop` fires → adapter → reducer → insert. These are separate hook events
with no connection.

**Why it's a problem:** The `Stop` event contains the assistant's response — which is
evidence about what kind of prompt the user sent. But the pipeline processes each event
independently. The `Stop` handler doesn't know about the prompt that preceded it, and
the prompt handler doesn't know about the response that followed.

**How Route C closes it:** The `Stop` handler (and potentially `PostToolUse` handlers)
emit evidence rows linked to the prompt via `turn_id`. The recompute step runs after
each evidence insert.

### Loop D: Stale denormalized kind

**What happens:** `session_prompts.prompt_kind` is set at insert time. If evidence later
changes the classification, the column holds the stale value.

**Why it's a problem:** Consumers reading `prompt_kind` directly (like `final-claim.ts`)
get the old classification. They have no way to know it's stale.

**How Route C closes it:** The recompute step updates `session_prompts.prompt_kind`
in place when the argmax changes. The column remains the denormalized current belief.
Consumers that need the full distribution can query `prompt_kind_evidence` directly.

## Design

### Schema

```sql
create table if not exists prompt_kind_evidence (
  evidence_id text primary key,         -- "{prompt_id}:evidence:{seq}"
  prompt_id text not null references session_prompts(prompt_id),
  kind text not null,                   -- the kind being evidenced
  score real not null,                  -- 0.0 to 1.0
  method text not null,                 -- see methods below
  evidence_ref text,                    -- what triggered this (turn_id, event_id, etc.)
  created_at text not null
);
```

No CHECK constraint on `kind` — the schema allows any string, matching the existing
`session_prompts.prompt_kind` design. The `PromptKind` union type in TypeScript
constrains what producers write.

### Evidence methods

| Method | When | What it captures |
|---|---|---|
| `positional` | Insert time | `prompt_index = 0` → direction_setting prior |
| `heuristic` | Insert time | Content-based classification from `classifyPromptKind()` |
| `contextual` | After assistant response | Response content, tool calls in the turn |
| `correction_signal` | After next user prompt | User corrects or redirects the assistant |
| `outcome` | After turn/session completes | Test results, session goal achievement |

### Re-weighting rule

Each evidence row is an independent observation. The current belief for a prompt is the
latest score for each kind, weighted by method reliability:

```
positional:  weight 1.0  (deterministic — index 0 IS direction-setting)
heuristic:   weight 0.6  (pattern matching — good but not perfect)
contextual:  weight 0.8  (response content — strong signal)
correction:  weight 0.9  (user explicitly correcting — very strong)
outcome:     weight 0.7  (test results — indirect but meaningful)
```

The argmax is the kind with the highest weighted score. If no kind exceeds a threshold
(0.5), the prompt stays as the initial classification.

### Recompute trigger

After each evidence insert, recompute the argmax for the affected prompt. If the argmax
changed, update `session_prompts.prompt_kind`. This is the loop-closing step.

### Type safety

```typescript
export type PromptKind =
  | 'direction_setting'
  | 'debugging_request'
  | 'question'
  | 'correction'
  | 'refactoring_request'
  | 'task_instruction'
  | 'follow_up'
  | 'assistant_response';
```

`RecordPromptBoundaryInput.kind` changes from `string` to `PromptKind`. The CLI `--kind`
flag validates against the union.

Original write-up kept below for context.

### R1: Extract classification from boundary construction

**Current:** `buildUserPromptBoundary()` in `src/adapters/shared.ts` calls
`classifyPromptKind()` inline and embeds the result in the boundary object.

**Target:** `buildUserPromptBoundary()` produces the raw boundary without a kind.
Classification is a separate step.

**Why:** Route C needs to record evidence rows alongside the classification. If
classification is embedded in boundary construction, the evidence recording is tangled
with object construction. Separating them makes the pipeline:

```
adapter → buildUserPromptBoundary() → raw boundary (no kind)
         → classifyPromptKind() → kind + evidence metadata
         → recordPromptBoundary() → insert with kind + evidence row
```

**Files:** `src/adapters/shared.ts`, `src/adapters/codex.ts`, `src/adapters/claude.ts`,
`src/reducers/observation.ts`

### R2: Move classifier to its own module

**Current:** `classifyPromptKind()` lives in `src/adapters/shared.ts` — an adapter
concern.

**Target:** Move to `src/classification/prompt-kind.ts` (new directory). The classifier
is a domain function, not an adapter utility.

**Why:** Route C adds more classification logic (contextual, correction, outcome
evidence). These don't belong in the adapter layer. A dedicated module makes the
pipeline stages explicit.

**Files:** Create `src/classification/prompt-kind.ts`, update imports in
`src/adapters/shared.ts`, `src/reducers/observation.ts`

### R3: Add PromptKind union type

**Current:** `RecordPromptBoundaryInput.kind` is `string` (free text).

**Target:** Add `PromptKind` union type in `src/types/observation.ts`. Change
`RecordPromptBoundaryInput.kind` from `string` to `PromptKind`.

**Why:** Route C introduces multiple evidence methods producing kinds. A union type
catches typos at compile time and documents the valid set.

**Files:** `src/types/observation.ts`, all files that construct or consume
`RecordPromptBoundaryInput`

### R4: Pass turn context to the Stop handler

**Current:** The `Stop` event handler creates an assistant prompt boundary independently.
It doesn't look up the preceding user prompt.

**Target:** The `Stop` handler queries `session_prompts` for the user prompt with the
same `turn_id`, and uses the response content to generate contextual evidence.

**Why:** This is how Loop C gets closed. The `Stop` handler is where contextual evidence
originates.

**Files:** `src/adapters/shared.ts` (or the new classification module),
`src/hooks/runtime.ts`

## What Route C does NOT do

- **No embedding-based classification** (Tier 3 from the SSR discussion). That requires
  an embedding model and is a separate work item.
- **No analysis consumer.** Route C makes classification trustworthy. A consumer that
  uses it for pattern analysis is a separate work item.
- **No retroactive re-classification.** Existing rows in `session_prompts` keep their
  current `prompt_kind`. Route C applies to new rows going forward. A migration script
  to backfill evidence rows for existing data is a separate (optional) work item.
- **No changes to `final-claim.ts`.** The consumer continues to filter on
  `prompt_kind = 'assistant_response'`. Since assistant kinds don't change, this is
  unaffected.
