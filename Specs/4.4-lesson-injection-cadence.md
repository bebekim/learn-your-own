# Lesson injection cadence for the night-shift pipeline

Priority: medium
State: draft

## Problem

Lessons are injected exactly once per pipeline run: `src/runner/run-pipeline.ts:135-157`
selects per role at prompt-build time and appends them (titles only,
blind-safe) to the round-1 writer prompts. Everything after that is static:

- **Rounds 2..N get no new lessons.** The feedback loop
  (`run-pipeline.ts:268-290`, `buildFeedbackPrompt`) sends only aggregate
  pass/fail counts. If round 2's failure reveals a failure class that has a
  promoted lesson, that lesson is never delivered — the loop cannot escalate
  its own scaffolding.
- **Spec pickup and `lyo pipeline init` consult no lessons.** Lessons enter
  at run start, not when a spec is chosen for review or compiled into a plan.

Infrequent injection loses twice: the scaffold benefit is forgone, and no
`lesson_application` row exists for the run, so no credit can accrue — the
posteriors starve, not just the agent.

Counterweight (from `Specs/3.1-counterfactual-credit-synthesis.md`): the null
arm must survive. Injecting every relevant lesson at every opportunity drives
propensities to 1 and makes ratio-lift unidentified. So the doctrine is
**maximize decision frequency, not injection frequency**: every decision
point is a logged inject-or-null choice with its propensity; Thompson (or the
failure trigger) decides, the log makes it countable.

## Desired Behavior

Cadence hooks, each a propensity-logged decision point, blindness preserved
throughout (titles/hashes only; spec-constraint vehicle shared with both
writers).

**No hard cap on injections.** Per `principled-map.md`, a fixed limit (the
"≤3 per role" in workflow-mechanics, the "top-2 / ≤3 pre-armed" in
`Specs/3-lesson-delta-design.md` §11.5, and its live embodiment
`DEFAULT_LESSON_LIMIT = 3` at `src/lyo/lesson-library.ts:42` — both
selection paths are top-k slices: `slice(0, limit)` in
`lesson-library.ts:124` and `selection-policies.ts:97`) is a magic number —
not an error rate, not data-derived, not a labeled scope decision.
Selection stays a sort-and-slice, but the slice bound is computed, not
chosen:

  inject top min(n_pass, n_budget) candidates by expected prevented loss

  n_pass   = #{ i : θᵢ × P(failure_class recurs | cell) × C_failure
                    > C_tokens(lesson i) }        — the economic gate
  n_budget = ⌊ lesson_block_token_budget / tokens_per_lesson ⌋
                                                  — from the plan artifact

Both bounds are `min()`/`max()` over measured quantities: θᵢ sampled from
the lesson's Beta posterior, recurrence from cell history (Specs/4.2),
failure and token costs from the cost accounting added by Specs/4.3, the
prompt budget from the plan. The rule parameterizes itself like Dijkstra's
edge weights — the data decides how many lessons is too many. Until 4.3's
cost terms exist, the interim values must be recorded in the plan artifact
as explicitly labeled scope decisions — never silent constants in code.

- **H1 — spec pickup.** When the night shift selects a spec for
  review/implementation, collect lessons whose failure classes or zones
  overlap the spec into the review context. Presentation only; no plan
  changes.
- **H2 — `lyo pipeline init`.** Spec-constraint lessons relevant to the
  compiled spec are evaluated at compile time and recorded as decisions
  (inject or null), even though delivery still happens at run start.
- **H3 — run start.** Unchanged: role-routed selection per writer (current
  behavior).
- **H4 — round boundary (failure-triggered only).** After each verify round,
  classify the round's failure signal; lessons whose failure class matches
  and that were not already delivered this run are injected into the next
  feedback prompt alongside the aggregate counts. Run-start selection is NOT
  re-drawn per round (no fresh Thompson per round — keeps propensity
  bookkeeping simple and prompts stable). Each round's trigger outcome —
  injected set or explicit null — is logged.
- **H5 — post-run.** Unchanged: outcome credit via `trace-consumer`
  (tightened separately by Specs/4.2). H4 deliveries must produce
  `lesson_application` rows like H3 deliveries do, so mid-run injections are
  creditable.

Every new decision point logs its propensity/decision record the way the
kernel store's `lesson_decision` log (§5.3, v0.2) already does — including
explicit nulls.

## Non-Goals

- No change to Thompson selection math, Wilson/LR gates, or counter rules
  (layer 3 machinery is consumed, not modified).
- No re-selection of the run-start set per round.
- No lesson content beyond titles/hashes inside writer stages (blindness
  invariant stands).
- No true mid-stage injection — stages are single-shot; round boundaries are
  the finest grain available.

## Edge Cases

- Failure signal matches no lesson failure class → explicit null decision,
  logged, nothing injected.
- Same lesson re-matches in a later round → already delivered this run; do
  not re-inject, but the non-event is not a new decision (avoid double
  counting).
- Failure-triggered lesson titles must not leak test content — titles are
  already blind-safe; spec-constraint vehicle remains the only shared one.
- `maxRounds: 1` (non-iterating runs) → H4 never fires; H1–H3/H5 unaffected.
- More candidates pass the stopping rule than the prompt budget can hold →
  rank by expected prevented loss (θᵢ × recurrence × C_failure), truncate at
  the budget, and log the cutoff as part of the decision record — the budget
  itself comes from the plan artifact, not a hardcoded number.

## Test Expectations

- A two-round fixture where round 1 fails with a known failure class: the
  matching promoted lesson appears in the round-2 feedback prompt, and a
  decision record (with propensity) is written.
- A run with no matching failure class logs an explicit null decision.
- A lesson delivered at H3 is not re-delivered at H4.
- Blindness: `checkBlindness` still passes; writer prompts contain titles
  only.
- Full suite green: `npm test`; `npm run typecheck`.

## Known Risks

- More injection points = more credit rows = slower per-cell evidence
  accumulation under 4.2's tightened rules; visible delivery rates may rise
  while promotion slows. This is the honesty tradeoff, accepted in advance.
- The stopping rule depends on 4.3's cost accounting landing first; without
  measured C_tokens and C_failure the threshold degenerates into the very
  magic number this spec forbids. If 4.3 slips, the interim scope decision
  must be revisited, not silently kept.
- Failure-class misclassification at round boundaries misroutes lessons;
  mitigated by logging the classified signal alongside the decision so bad
  triggers are auditable.
- Draft state rationale: the Specs/0 gate decision and 4.2's landing may
  reshape the credit and decision-record details before this is ready.
