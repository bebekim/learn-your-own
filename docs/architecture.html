Architecture design

LYO captures agent work, stores observations, and uses evidence to decide when to offer advice. Learning rules belong at the center. Hooks, commands, and databases connect those rules to the outside world.

Swapping lesson selectors

Design proposal · ordinary lessons

Both the session hook and store would call one application use case. A versioned configuration would select the strategy for each stage. Comparing two strategies would require changing that configuration in one place.

One request and one receipt

The request carries pre-decision cues, eligible lesson versions, the slot limit and a reproducible draw source. The receipt identifies both strategy versions, their configuration and feature or index snapshots, the candidates considered, the ordered selection and its reasons. Distinguish an empty pool, deliberate abstention and unavailable inputs. An unavailable index must be visible if a configured fallback runs.

Comparable experiments

Hold the request, eligible pool and budget fixed when comparing selectors. Log whether inclusion probabilities are exact, estimated or unknown. Similarity scores cannot stand in for probabilities. A randomized retrieval stage also affects inclusion. Evaluating a multi-lesson action as a unit requires its joint selection probability.

Current gaps and the acceptance check

The store’s decision API can inject a sampler. Its input contains an ID and two Beta parameters. The ordinary session hook and convenience store API resolve the default directly. In an isolated one-candidate, one-slot probe, an always-abstaining policy returned zero picks while the store recorded inclusion probability 1 for that candidate. The current shortcut assumes every fitting candidate will be chosen. Store · Sampling contract · Hook

Acceptance requires switching a versioned profile through configuration and exercising both entry points. Check parity on the same eligible inputs, excluded IDs staying excluded, a permitted silence decision with truthful probability, and a visible reason for every injected lesson. Run the existing Thompson profile against seeded historical fixtures for compatibility. Registered findings retain their own reviewed activity and trial rules. Candidate algorithms

How one mark changes another lesson’s odds

Implemented · ordinary lesson selection

Suppose lesson A came with a 90% confidence estimate. Four harmful marks have accumulated. The store waits for a total feedback weight of five before using A to judge how much weight to give model estimates across the library. Change just the fifth mark below and watch what happens to lesson B.

Controlled example · one selection slot
65.0% chance B wins the slot
A has too little feedback to contribute. The default prior weight is γ = 1. B draws from Beta(2.60, 1.40).
52.7% chance B wins the slot
A now contributes. Its observed helpful fraction is 0, so agreement with its 0.90 estimate is 0.10. The shared weight falls to γ = 0.10. B draws from Beta(1.16, 1.04).

A belongs to a different failure class from B. B and C compete under the store’s default Thompson sampler. Both have zero feedback. B has an 80% estimate with strength 2. C has no estimate and draws uniformly. Given B’s draw x, the chance C draws below it is x, so B’s exact winning probability here equals its Beta mean. With a different competitor or multiple slots, that shortcut no longer holds.

The local update

For each eligible lesson with a usable estimate and feedback weight of at least five, compute agreement = 1 − |observed helpful fraction − estimated confidence|. Average these values to obtain γ, using 1 when no lesson qualifies. The store uses its library view. The prompt hook computes γ over its filtered pool. Calibration rule · Hook scope

The system effect

Each eligible prior contributes γ × strength pseudo-counts, split between helpful and harmful according to its confidence. Changing γ can change which lessons win the next draw. Recorded feedback and Wilson status thresholds stay independent of these pseudo-counts. No iteration to equilibrium is required. Store selector · Controller tests

Counterexample. A model that always predicts 50% earns perfect agreement on lessons with a 50% helpful fraction. It can still be useless for choosing between them. To test benefit, register a prediction and compare measured outcomes under advice and no advice. Trial design

One decision for live updates and replay

  1. LessonStore supplies the current status and the helpful and harmful counts. Replay reconstructs those counts from recorded marks.
  2. lessonStatusChange evaluates the same Wilson thresholds for both callers. It returns a transition or leaves the status in place.
  3. The live store persists the transition and records the upper bound for quarantine. Replay applies the transition in memory.

One helpful and seven harmful marks leave a candidate eligible. One more harmful mark triggers quarantine. See the boundary case

An application port supplies finding state

  1. The session hook passes the current activity cue into selection.
  2. The interface adapter reads candidate IDs and supplies the selector with state lookup, trial management status, and hashing.
  3. The application selector checks activity and validity. A repository match alone cannot select a finding.
